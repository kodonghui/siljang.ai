# 장부 쓰기 중복 확인 결정

설계 판단(실장님, 2026-11-28, 이유: 구글 메타데이터 한도): 기존 장부 열 뒤에 숨긴 ‘실장님 기록 ID’ 열을 두고 이벤트의 개인정보 없는 ID를 같은 행에 씁니다. 헤더 메모는 열을 지우거나 바꾸지 말라고 안내합니다. 메타데이터는 열 위치의 고정 표지에만 쓰며 이벤트마다 쌓지 않습니다. 기존에 서명한 12개 열은 그대로 두고 끝에 숨김 열 하나를 삽입해 표지를 갱신합니다. [구글의 저장 한도](https://developers.google.com/workspace/sheets/api/guides/metadata#metadata_storage_limits)는 시트당 30,000자입니다.

정상 갱신에서는 주문번호 열만 읽어 0행이면 추가하고 1행이면 갱신합니다. 둘 이상이면 덮어쓰지 않습니다. 결과를 받지 못한 쓰기는 구글의 [처리 제한 180초](https://developers.google.com/workspace/sheets/api/limits)보다 긴 5분 뒤 숨긴 ID 열을 확인합니다. 확인 범위는 ID 열 전체와 최근 1만 행 중 작은 범위입니다. 재시도 뒤에도 먼저 보낸 요청이 늦게 반영될 수 있어 30분 간격, 최대 24시간과 48회까지 확인합니다. 실패 시험에서 늦은 최초 추가가 재시도 뒤 적용되어 두 행이 생기는 경우를 재현했습니다.

실장님 최종 판단(Orca, 2026-11-28): “중복 행은 자동으로 지우지 않고, 사장님 할 일(기존 할 일·알림 경로)로 '장부에 같은 주문(주문번호 …)이 두 줄 있어요. 하나를 지워 주세요'를 한 번 알려요.” 중복이 남으면 갱신을 멈추고, 사장님이 한 줄을 지운 뒤 이어 갑니다. 같은 주문의 알림은 한 번만 보냅니다. SPEC-064의 주문당 한 행은 사후 확인과 사장님의 중복 해결이 끝난 뒤의 상태로 봅니다. 24시간 이후에 아주 늦게 반영된 중복은 다음 주문 갱신 때 발견합니다.
