# 장부 쓰기 중복과 편집 경합 결정

설계 판단(실장님, 2026-11-28, 이유: 구글 메타데이터 한도): 기존 장부 열 뒤에 숨긴 ‘실장님 기록 ID’와 ‘실장님 주문 ID’를 둡니다. 개인정보가 아닌 이벤트 ID와 주문 ID를 같은 행에 쓰고, 헤더 메모로 열을 지우거나 바꾸지 말라고 안내합니다. 메타데이터는 열 위치의 고정 표지에만 쓰며 이벤트마다 쌓지 않습니다. 기존에 서명한 12개 열을 유지하고 숨김 열을 뒤에 삽입합니다. [구글의 저장 한도](https://developers.google.com/workspace/sheets/api/guides/metadata#metadata_storage_limits)는 시트당 30,000자입니다.

정상 갱신은 쓰기 전후 우리 열의 행 집합을 비교하고 대상의 주문 ID를 다시 확인합니다. 다른 주문이 사라졌으면 이전 값을 빈 행에 되살리고, 복구 뒤에도 다른 행을 비교합니다. 충돌이나 5,000행 초과에는 해당 쓰기를 멈추고 사장님 할 일로 알립니다. 우리 열에 대한 사장님의 편집도 충돌로 안내합니다. 다른 주문이나 사장님 열을 자동으로 지우지 않습니다. 이 방식은 구글의 원자적 조건부 쓰기가 없어 조회와 쓰기 사이의 아주 짧은 경합을 완전히 막지 못하며, 동시 편집과 복구가 겹치면 다시 확인이 필요합니다. [구글 배치 설명](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets/batchUpdate)은 협업자의 변경과 배치 결과가 겹칠 수 있다고 밝힙니다. 실장님이 2026-11-28에 승인한 전체 열 비교는 오랑이의 자동 갱신 유지 결정(사용자님의 주말 위임)에 따른 것입니다. 드라이브 version은 우리 쓰기에도 바뀌고 증가 폭이 정해지지 않아 충돌의 판정 기준으로 쓰지 않습니다. [출시 확인](release-checklist.md)을 남겼습니다.

실장님 판단(2026-11-28, 중단 뒤 경우만): 같은 실행 안에서는 쓰기 전 시트 내용을 메모리에서 비교해 기존처럼 복구합니다. 중단 뒤에는 주문별 HMAC 비교 기준만 데이터베이스에 보관하고, 소실이나 변경이 의심되면 자동 복구하지 않고 영향 주문의 사장님 할 일로 알립니다. 삭제된 오래된 주문의 이름과 연락처가 시트에 남아 있어도 우리 데이터베이스에 다시 수집하지 않기 위한 결정이며, 앞 결정의 복구 실패 시 알림과 같은 범위입니다.

결과를 받지 못한 쓰기는 구글의 [처리 제한 180초](https://developers.google.com/workspace/sheets/api/limits)보다 긴 5분 뒤 확인합니다. 사후 확인의 이벤트 ID 범위는 전체와 최근 1만 행 중 작은 범위입니다. 재시도 뒤 늦게 반영될 수 있어 30분 간격, 최대 24시간과 48회까지 확인합니다. 늦은 최초 추가가 재시도 뒤 적용되어 두 행이 생기는 경우를 회귀 시험으로 재현했습니다.

실장님 최종 판단(Orca, 2026-11-28): “중복 행은 자동으로 지우지 않고, 사장님 할 일(기존 할 일·알림 경로)로 '장부에 같은 주문(주문번호 …)이 두 줄 있어요. 하나를 지워 주세요'를 한 번 알려요.” 중복이 남으면 갱신을 멈추고, 사장님이 한 줄을 지운 뒤 최신 값을 다시 적습니다. 같은 주문의 알림은 한 번만 보냅니다. SPEC-064의 주문당 한 행은 사후 확인과 사장님의 중복 해결이 끝난 뒤의 상태로 봅니다. 24시간 이후에 아주 늦게 반영된 중복은 다음 주문 갱신 때 발견합니다.

## CPU 측정과 출시 조건

2026-11-28 로컬 Node 22.23.4에서 실제 장부 쓰기 함수를 합성 응답으로 실행하고, 세 번 준비 실행 뒤 열 번의 프로세스 CPU 시간을 측정했습니다. 외부 호출은 없고 전후 스냅숏 응답은 측정 전에 만들었습니다.

| 행 수 | 스냅숏 크기 | CPU 최솟값 | 중앙값 | 최댓값 |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 181 bytes | 0.545ms | 0.662ms | 0.859ms |
| 1,000 | 163,909 bytes | 10.119ms | 16.242ms | 22.665ms |
| 5,000 | 823,909 bytes | 47.087ms | 57.722ms | 114.376ms |

프로세스 CPU에는 합성 응답 처리가 포함되며 실제 Cloudflare Workers CPU 측정은 아닙니다. 스테이징의 Workers Free에서는 큰 장부가 CPU 한도에 걸릴 수 있습니다. 출시는 사용자님이 2026-11-23 Orca 항목 16에서 정한 Workers Paid 전제이며, [Cloudflare 문서](https://developers.cloudflare.com/workers/platform/limits/)의 1시간 미만 간격 Cron 기본 CPU 한도는 30초입니다. 실제 Paid 전환과 스테이징의 큰 장부 실행은 확인하지 않았습니다.

재리뷰 수정 뒤 같은 방식으로 다시 측정한 CPU 시간은 1행 최솟값 0.830ms·중앙값 1.210ms·최댓값 1.379ms, 1,000행 13.453ms·18.375ms·33.024ms, 5,000행 68.176ms·77.449ms·124.558ms입니다. 대상 행의 마지막 서명을 비교하고 쓰기 직전 전체 행을 다시 읽는 코드가 포함된 로컬 측정이며 실제 Workers 측정은 아닙니다.

대상 행의 사장님 수정은 개인정보 원문 없이 이전 행의 앱 서명과 비교해 탐지합니다. 수식으로 시작하는 셀은 원래 입력 유형을 추가로 확인해 수식과 같은 글자를 구분하고 복구할 때 수식을 보존합니다. 사장님 열의 마지막 자료 때문에 5,000행을 넘는 추가·복구도 중단합니다.

2026-11-28 재리뷰 수정 후 행별 HMAC 생성과 비교 기준 JSON 생성을 포함해 같은 로컬 방식으로 다시 측정했습니다. 1행 CPU는 최솟값 1.121ms·중앙값 2.034ms·최댓값 4.187ms, 1,000행은 96.375ms·112.045ms·155.225ms, 5,000행은 512.755ms·599.664ms·767.816ms입니다. 외부 데이터베이스 호출과 실제 Workers의 CPU는 측정하지 않았습니다. Free 스테이징에서 큰 장부는 CPU 한도에 걸릴 수 있으며 실사용 출시는 Workers Paid 전제입니다.
