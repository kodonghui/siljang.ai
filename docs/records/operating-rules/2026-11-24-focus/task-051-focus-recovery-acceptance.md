# TASK-051 이동 초점 복구 대조

PR #212의 CI137973935908과 앞선 로컬 전체에서 조문을 넣은 뒤 초점이 textarea 대신 body에 남았습니다. 첫 수정은 실패한 이동 요청을 다음 렌더까지 보존했지만,실제 Claude 검토7113218554에서 사용자가 다른 필드로 옮긴 초점을 다시 빼앗는 문제를 발견했습니다. 아래가 현재 구현입니다.

실제 검토7113218554의 중간1/낮음4건을 처리했습니다. 세 ref를 단일 초점 요청으로 모아 새 요청이 이전 요청을 바꿉니다. useLayoutEffect의 같은 화면 반영에서 요청을 소비하고,연결된 활성 대상의 첫 focus가 실패하면 한 번만 다시 시도합니다. 이미 다른 요소로 초점이 옮겨졌거나 입력이 잠겼으면 요청을 버리고 adopt에서도 비웁니다. 다음 렌더/사용자 입력을 기다리는 재시도는 없습니다. 필드 오류가 이전 조문 요청 뒤에 막히지도 않습니다.

이전 head에서 같은 commit 복구/다른 필드 타이핑2개가 실패했습니다. 수정 후 조문·단계 삭제·필드 오류의 대상별 모의와 첫 실패 단언,두 실패 뒤 사용자 입력/새 필드 오류를 포함한 전체 웹49파일1,106개·타입 종료0·형식/lint433파일1042ms·빌드881ms와 두 Worker가 통과했습니다. 서버/DB/의존성은 앞서 새 빈 DB34개 마이그레이션·서버2,221개를 통과한 원본과 같습니다.

| 검토 | 처리 |
| --- | --- |
| 1. 끝없는 요청/사용자 초점 탈취·요청 간 막힘·adopt 잔여 | 단일 요청을 같은 commit에서 소비하고 두 번 이내 종료,사용자 이동/잠금 시 취소,adopt 초기화 |
| 2. 다음 렌더가 있어야 복구 | useLayoutEffect에서 첫 실패 한 번만 재시도. 추가 rerender 없이 단언 |
| 3. 실제 실패 단언/다른 경로 시험 없음 | 정확한 조문 조건/단계 버튼/오류 입력 대상만 모의,첫 실패 시 activeElement 불일치와 호출 수·최종 초점 단언 |
| 4. 다른 편집기 경로 | TASK-049/053 후속으로 대조. 한 WBS 한 PR 규칙에 따라 분리 |
| 5. 기록 제목 | 괄호 뒤 마침표 제거 |

## 확인의 한계

기존CI가 첫 focus를 놓친 정확한 환경 조건은 아직 확인하지 못했습니다. 시험은 같은 body/textarea 증상과 복구/초점 탈취를 결정적으로 모의합니다. 실제 학원컴 키보드/화면은 공통 Aside CLI CDP 보류로 미확인입니다. 다른 PriceListEditor/PaymentDestinationEditor의 먼저 지우는 경로는 WBS별 TASK-049/053 후속 후보로 기록하며 이 PR에 함께 넣지 않습니다. 기록612의 제목 형식도 맞췄습니다.

원래 CI의 환경 원인을 찾았다고 쓰지 않습니다. 타이머·대기 시간·시험 제한은 늘리지 않았습니다. 앞선 전체 새 빈 DB 검사는34개 마이그레이션·서버104파일2,221개·웹1,103개/빌드746ms를 통과했고,이번 발견 처리 뒤 서버는 바뀌지 않았습니다. 다음은 현재 head CI app/db·병합 직전 Codex 리뷰 한 번·squash 뒤 main CI/배포/실제 원격 앱 태그입니다. PR #212는 그 main을 결합합니다.
