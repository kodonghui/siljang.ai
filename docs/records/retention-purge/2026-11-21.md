## 공통 규칙과 임시 파일

- A16: 주문·상담 하나의 중간 오류는 내용·보관 기록·파일 대기를 함께 되돌립니다. 잠긴 행은 건너뛰고 동시 실행은 한 번만 처리합니다. 파일 저장소를 기다리며 DB 잠금을 잡지 않습니다.
- A22: 보통 ID 조회와 새 명령의 참조에서 보관 주문·연결 결제/환불/변경/신고를 제외합니다. 보관 이름은 운영자·지우기 범위만 직접 참조합니다(`purge-visibility.test.ts`). 개별 목록 API와 운영자의 사유·접속기록은 각각의 작업에서 이 조건을 이어 지켜야 합니다.
- 상담 잠금을 잡은 중 실제 수신 저장 함수를 별도 연결에서 실행해 새 상담을 확인했습니다. 키까지 지운 뒤 같은 채널의 메시지도 새 손님·상담으로 받습니다. 실제 카카오 앱의 확인 결과는 아닙니다.
- `purge-uploads.test.ts`: 세 용도의 임시 파일은 실제 발급 형식과 한 시간 경계를 확인합니다. 새 파일·영구 사진·알 수 없는 경로를 보존합니다. 목록 페이지·시간 예산 뒤 이어가기와 실패 후 다음 날 재확인을 검사합니다.
- `purge-runner.test.ts`: 독립 DB에서 여덟 차례·차례별 숫자 기록·다른 가게 보호·같은 날 한 번·동시 시작 한 번·행별 실패·한 행 배치·시간 예산 중단·저장소 설정 없음을 확인했습니다. 시험 뒤 그 독립 DB만 지웠습니다.
- 전역 후보 조회는 ID·시각·존재 여부만 돌려주고, 내용은 가게 범위의 짧은 트랜잭션에서 다시 확인합니다. 정적 검사는 내용 반환·쓰기·다른 파일의 같은 SQL을 거절합니다. 운영 기록과 로그에는 내용·저장 위치를 남기지 않습니다.

## 실제 환경에서 남은 확인

사진 저장소의 성공·실패·시간 초과와 재시도는 메모리 구현으로 확인했습니다. 기존 S3 모듈의 계약 시험도 전체 검사에 포함했습니다. 실제 S3 호환 저장소 시험을 위해 로컬 MinIO 이미지를 받으려 했지만 Quay·Docker Hub에서 두 번 모두 접근이 거절됐습니다. 그 준비는 중단했고 컨테이너를 만들거나 계정·요금을 바꾸지 않았습니다.

실제 S3의 파일 삭제와 스테이징 Cron의 03:00 실행은 미확인입니다. 스테이징 연결·비밀 값 확인(TASK-173)에서 함께 확인할 항목으로 남깁니다. WBS의 자동 수락 시험 통과와 이 직접 확인을 구분합니다. 법률 답을 기다리는 3·5년의 잠정 기간은 설계대로 두었습니다.
