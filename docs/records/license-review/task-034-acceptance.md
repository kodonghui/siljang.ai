# TASK-034 수락 조건 대조

SPEC-003과 API-012/013/014의 서버 구현입니다. 실제 Supabase/TOTP 로그인·기존 역할의 권한 적용·사장님 카카오 알림 수신은 대기이며 로컬 합성 세션을 실제 인증 성공으로 세지 않습니다.

| 조건 | 확인한 것 |
| --- | --- |
| SPEC-003 #1 | 현재 계좌가 있는 pending 가게를 verified로 정하면 가게와 그 계좌에 같은 운영자/시각이 함께 남습니다. 대표자/상호와 다른 예금주도 운영자가 정할 수 있으며 원문 계좌를 읽거나 응답하지 않습니다. |
| SPEC-003 #2 | 현재 계좌가 없으면 확인됨은409 payment_account_missing이고 보류는200입니다. |
| SPEC-003 #3·G4 | 보류 이유는 가게와 할 일에 남고 같은 트랜잭션에서 알림 대기 행을 한 번 넣습니다. 같은 요청 키 재전송은 추가하지 않습니다. 알림을 실패로 남겨도 이유는 할 일에 남습니다. 알림 DB INSERT 자체가 실패하면 판정/할 일도 되돌고 같은 키로 다시 처리할 수 있습니다. 실제 발송은 미확인이며 Event API 발신은 TASK-167 출시 검토입니다. 예약 링크는 만들지 않습니다. |
| G1 | 실제 로컬 사장님 세션은 내 정보200·운영자 세 경로401입니다. 가짜 범위·진짜 사장님 범위는 운영자 목록 기능을 받지 못하고 SQL0건입니다. 운영자는 선택한 A/B 가게를 읽되 계좌 끝4자리와 등록 정보만 보고 고객 ID/계좌 원문은 보이지 않습니다. A 판정은B 기록을 바꾸지 않습니다. |
| G2·G3 | 같은 요청 키는 처음 결과의 현재 상태, 다른 본문은422입니다. 가게·현재 계좌·대기 중인 신원 변경을 함께 가리키는 불투명 버전으로 CAS를 합니다. 두 운영자의 동시 판정은200/409 already_decided, 다른 변경은409 version_conflict입니다. 확인됨 재확인은unchanged이고 보류로 되돌리기는409 invalid_state입니다. |
| 사업자 변경 | pending 요청은 서명된 증빙 주소/새 값/이전 값으로 보입니다. 확인됨만409 identity_change_pending이고 보류는 가능합니다. 요청이 생기면 기존 화면의 버전도 바뀝니다. 요청 판정 자체는 TASK-036입니다. |
| 목록/중복 | 기본pending·20개,1~100개, 만든 시각/ID 오름차순입니다. 커서는 마이크로초를 유지해 동률/다음 쪽을 빠뜨리거나 되풀이하지 않습니다. 중복 번호는 목록에 표시하고 상세는 오래된20가게까지입니다. 상태가 다른 커서/잘못된 입력은422입니다. |
| 권한 | 새0029 함수는 고정 검색 경로·명시한public 테이블·공개 실행 금지입니다. 살아 있는 운영자/세션과 현재 상태를 다시 검사해 가게/현재 계좌만 갱신합니다. 최소 역할은 조회2문장·함수 실행1문장이며 일반 승인/예금주 확인 UPDATE는 로컬 새 역할에서42501입니다. 함수 EXECUTE를 빼면500, 복구 뒤200입니다. |
