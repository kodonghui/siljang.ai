### 1-3. 기술 스택(결정됨, `docs/10-wbs/tech-stack.md`)

- **서버:** Cloudflare Workers + Hono, TypeScript strict(`app/server`).
- **웹:** React + Vite(`app/web`). 웹 빌드를 같은 Worker가 정적 자산으로 준다. API는 `/api` 아래에 있다.
- **데이터베이스:** Supabase PostgreSQL(서울), Hyperdrive, 드라이버 `pg` 8.23.1. 요청마다 새 Client를 만든다.
- **사진 저장소:** Supabase Storage의 S3 호환 주소(`aws4fetch`).
- **운영자 인증:** Supabase Auth의 이메일·비밀번호와 TOTP 2단계 인증(06 DEC-27).
  - 사장님 인증은 카카오 로그인(TASK-020)이며, 카카오 시험 결과(TASK-011)를 기다린다.
- **AI:** 두 회사의 LangChain 채팅 모델 가운데 배포 설정으로 고른다(`server/src/` 모델 호출 모듈, TASK-026). 호출마다 `ai_calls` 한 행이 남는다.
- **도구:** Node 22.23.4(`.nvmrc`), npm workspaces, `package-lock.json`, TypeScript 7, Vitest 5, Biome, Postgres 16.15(CI).
- **CI:** `.github/workflows/app.yml`·`db.yml`. 모든 PR과 main push에서 돈다.
  - app: 설치·린트·타입 검사·시험용 데이터베이스(마이그레이션 전부)·시험·빌드·키 검사.
  - db: 마이그레이션과 규칙 테스트.
  - `REQUIRE_DATABASE_TESTS=1`이라 CI에서는 데이터베이스 시험을 건너뛰지 않는다.

  - (b) 서버에서 WebP만 픽셀 회전
  - (c) 방향이 기본이 아닌 WebP는 JPEG로 바꿔 저장
  - (d) 그런 WebP는 422로 거절
- **원본:**
  - 04 G10

  - WebP: VP8X의 EXIF·XMP 청크를 빼고 플래그를 맞춘다.

  - (c) 그 밖의 방법.
  - HEIC는 방향이 EXIF가 아니라 `irot`·`imir` 속성이라 영향이 다르다.
- **ICC 색 프로필:** 위치·기기·시각 정보가 아니다. 지우면 넓은 색역 사진의 색이 바뀐다. 남길지 고르고 이유를 적는다.

## 5. 작업 하나를 하는 차례

1. **최신 main에서 브랜치를 만든다.**
   - 브랜치 이름은 `codex/task-<번호>-<짧은-영문>`이다(예: `codex/task-183-exif`).
   - `main`과 `claude/*`, `hands-on/*` 브랜치에는 push하지 않는다.
2. **원본을 읽는다(4-2).** 끝난 조건과 수락 기준을 한 줄씩 체크리스트로 옮겨 둔다.
3. **설계 쟁점을 정리하고 고른다.**
   - 원본에 답이 있으면 그대로 따른다.
   - 원본에 없고 되돌릴 수 있는 기술 선택은 네가 고른다. 대안·추천·반론과 공식 문서 확인 날짜를 README에 적는다.
   - 제품 결정(보이는 문구의 큰 변화, 요구사항 범위, 돈, 개인정보 처리, 보관 기간, 외부 서비스 추가)은 고르지 않는다. 추천안과 함께 동희님 확인 요청으로 보고하고, 그 부분만 열린 질문으로 둔다.
4. **실패하는 시험부터 쓴다.** 그 시험이 지금 코드에서 실패하는 것을 확인하고 커밋한다.
5. **구현한다.** 6절 코드 규칙을 지킨다.
6. **설계 문서를 고칠 일이 생기면** 생성기로만 고친다(7절). 바뀐 단계 README의 '확정한 뒤 고친 것' 표에 한 행을 더한다.
7. **검사한다(8절).** 결과 줄을 PR 본문에 그대로 옮긴다.
8. **기록한다(9절).**
9. **PR을 연다(10절).** 작업을 마치고 리뷰 준비 상태로 연다. CI app·db가 통과할 때까지 고친다.
10. **합치거나 보고한다(10절).**
11. **커밋은 일찍, 자주 한다.**
    - 첫 시험을 쓰면 첫 커밋과 push를 한다. 그 뒤로는 단계마다 커밋과 push를 한다.
    - 앞 개발 세션이 커밋 없이 긴 작업을 하다 한도에 걸려 일을 잃을 뻔했다(fix-log (404)).

  - 새 오류 코드가 필요하면 06을 생성기로 먼저 고치고, 서버 `problem.ts`와 웹 `problems.ts`(G7 표)를 함께 고친다.
- **경로 선언:** 라우터에 직접 붙이지 않고 `routes.ts`의 `APP_ROUTES`에 선언한다.
  - `shopRoute`: 가게 기록. 처리기는 `ShopRequest`만 받고, 가게 범위 연결 `ShopDb`가 `$1`을 늘 가게 ID로 채운다.
  - `ownerRoute`: 가게가 정해지기 전의 사장님 API.
  - `operatorRoute`: 운영자 API(TASK-021).
  - `openRoute`: 누구나 열 수 있는 경로. 이유를 적는다.
  - 06 계약과 견주는 시험이, 세션 보안이 걸린 API가 맞는 쪽으로 선언됐는지 본다.
- **가게 범위:** 새 가게 범위 API는 교차 가게 시험 스위트의 등록 목록 `CROSS_SHOP_CASES`(`server/test/support/cross-shop.ts`)에 등록한다. 빠지면 CI가 실패한다.
  - 가게 조건이 없는 SQL은 실행 때 막힌다. 규칙은 `sql-scope.ts` 첫머리에 있다.
  - 다른 가게·없는 ID·형식이 틀린 ID는 모두 같은 '찾을 수 없음'이다(G1).
- **쓰기 명령:** `request-key.ts`의 `runCommand`로 처리한다(`Idempotency-Key`, G2, 06 DEC-04). 명령의 쓰기와 '끝남' 표시는 같은 트랜잭션이다.
- **시각:** `time.ts`를 쓴다. 저장은 UTC이고, 셈은 가게 시간대로 한다(G8). 날짜와 `timestamp`는 JS Date로 바꾸지 않는다.
- **동시성:** 셈과 차례가 걸린 곳은 행 잠금(`FOR UPDATE`)이나 트랜잭션 잠금을 쓴다. 잠금을 빼면 동시 시험이 실패하는 것까지 확인한다(앞 작업들의 방식).
- **암호화:** `field-crypto.ts`(봉투 `v<버전>:…`, AAD는 쓰는 곳·가게·버전)를 쓴다. 평문 계좌번호를 데이터베이스·로그에 남기지 않는다.
- **접속기록:** 사장님·운영자가 손님 개인정보를 읽거나 바꾸는 요청은 응답과 같은 트랜잭션에 접속기록 한 행을 남긴다(SPEC-074, TASK-024).
- **일 실행기:** 서버 안의 일은 TASK-023의 일 등록부로 등록한다. 같은 일은 한 번만 실행된다.
- **바깥 서비스:** 시계·저장소·한도·서명 주소·인증 같은 바깥 서비스는 `services.ts`가 주입한다. 시험은 `createApp({ services })`로 모의 구현을 넣는다.
- **Node 형식 금지:** 서버 코드는 Node 형식을 쓰지 않는다. Workers 런타임 타입만 쓰고, 시험만 Node를 쓴다.
- **새 의존성:** 꼭 필요할 때만 더한다.
  - 정확한 버전으로 고정한다.
  - 나온 지 일주일 넘은 버전만 쓴다(`npm install --before=<일주일 전 날짜>`).
  - 이유를 README에 적는다. 이 저장소는 supabase-js 없이 `fetch` 어댑터를 썼다(TASK-021).

## 9. 기록

PR마다 아래를 같은 PR에 넣는다.

1. **`docs/records/progress.md` 맨 위 단락.**
   - 제목: `### YYYY-MM-DD HH:MM 무렵 KST · TASK-nnn 제목`
   - 때: 앞 PR 번호, 시작한 main SHA, 그 main에서 돈 app·db 실행 번호와 결과. GitHub에서 확인한 값만 적는다.
   - 한 일
   - 고른 것과 이유
   - 확인한 것: 명령 이름과 출력에서 옮긴 숫자.
   - 확인하지 않은 것
   - 직접 해보기 남음
   - 열린 질문
   - 실수와 고친 것
   - 동희님 말은 말 그대로, 시각과 어디서 했는지를 함께 적는다.
2. **`docs/records/fix-log.md`.** 이번 작업에서 배운 작업 규칙을 끝에 단락 하나(제목 `## PR <번호> — TASK-nnn …`)로 더한다.
   - 번호는 main의 마지막 다음이다. 늘 main의 fix-log 끝에서 다시 확인한다.
   - 앞의 번호와 글은 바꾸지 않는다.
3. **`app/README.md`.**
   - 번호 항목 끝에 새 항목을 더한다(main `c6b3a85` 기준 97까지).
   - 쓸 내용: 층, 고른 것과 이유, 시험, 설정 이름(값 없이), 직접 해보기 남음과 따라 할 명령, 인계할 것.
   - 머리 문단의 작업 목록도 고친다.
4. **WBS 끝남 표시.** 끝난 조건이 모의·로컬 시험만으로 모두 채워지면 PR CI 통과를 GitHub에서 확인한 뒤 표시한다.
   - `wbs_rows.py`의 그 작업에 `finished='YYYY-MM-DD, PR #n 합침…(뜻만)'`을 더한다.
   - 그다음 `build_wbs.py . --write`를 돌린다(검사 15: 날짜로 시작, 앞선 작업이 모두 끝나야 함).
   - 진짜 환경이 끝난 조건에 있으면 표시하지 않고 '직접 해보기 남음'으로 둔다(TASK-021·027 앞선 예).
   - `finished`에는 금지어('승인' 등)를 쓰지 않는다.
5. **끝난 조건 고치기.** 끝난 조건이나 다른 작업의 필드를 고쳐야 하면 `wbs_rows.py`를 고친다. 이유를 `docs/10-wbs/README.md` 10절 '확정한 뒤 고친 것'에 한 행으로 더한다.
6. **Notion·Miro·Artifact는 손대지 않는다.** 동희님 지시로 기록은 Git에서 관리하고 Notion에는 일의 끝에 한 번 올린다. 올릴 것은 `docs/10-wbs/README.md`의 '다음 올리기 목록'에 한 줄 더한다.

## 10. PR 형식과 합치기

**PR 본문**
- 11단계 계약 형식으로 쓴다(이 저장소의 앞 PR #60~#72를 보고 맞춘다).
- 첫 줄: 추적 ID. 예: `TASK-183 · REQ-269 · G10 · API-007`
- 절 차례:
  - `## 무엇`
  - `## 고른 것과 이유`
  - `## 계약 시험`(06과 견주는 시험)
  - `## 시험`(시험 수 앞뒤, 단계 검사 결과 줄, 조건을 하나씩 빼 시험이 실패함을 본 것)
  - `## 제공·수용`(제공한 것, 수용 상태. 직접 해보기가 남으면 '아직 아님')
  - `## 시험하지 않은 것`(직접 해보기 남음, 열린 질문)

**제목과 커밋**
- PR 제목: `feat(TASK-nnn): …`, `docs(...)`, `fix(...)`처럼 Conventional Commits 형식이다. 커밋 메시지도 같다.
- 커밋·PR 본문에 AI 모델 이름을 넣지 않는다.

**PR 리뷰와 GitHub 댓글**

- GitHub 댓글은 [AGENTS.md의 PR 리뷰](../../AGENTS.md#pr-리뷰)에 정한 절차에 쓴다.
- 발견 사항마다 고친 내용과 커밋 또는 고치지 않는 이유를 PR 댓글에 적는다. 코드 지적을 고칠 때는 같은 종류의 문제를 함께 찾고 실패하는 시험부터 쓴다. 처리 결과를 기록한 뒤 해당 스레드가 있으면 해결 표시(resolve)를 한다.
- 같은 종류의 지적을 후속 PR에서 처리할 때는 범위와 이유를 처리 댓글에 적는다.

**합치기**
- 검사(CI app·db 포함)와 [AGENTS.md의 PR 리뷰](../../AGENTS.md#pr-리뷰) 조건을 충족하면 합친다.
  - 병합 직전 Codex 리뷰를 요청하기 전에 `origin/main`을 확인한다. 앞서 있으면 rebase하고, 새 head의 CI가 통과할 때까지 기다린 뒤 Claude 리뷰 적용 여부를 확인한다.
  - squash로 합치고, 자동 합치기는 쓰지 않는다.
  - 합친 뒤 main에서 도는 app·db CI가 통과했는지 보고, 원격 main SHA를 기록한다.
- 네 환경에서 합칠 수 없으면 '합칠 준비 됨'(PR 번호, 머리 SHA, CI 실행 번호와 결과)으로 동희님께 보고하고 멈춘다.
- 합친 뒤 다음 작업은 최신 `origin/main`에서 새 브랜치로 시작한다.
- 금지: 강제 push(자기 브랜치의 rebase 뒤 `--force-with-lease`는 됨), main 이력 고치기, `reset --hard`, `stash`, 일괄 `clean`.

## 11. 글쓰기 규칙

- **언어:** 문서·기록·PR·커밋·보고는 한국어로 쓴다. 동희님께 하는 보고는 존댓말로 쓰고, '동희님'이라고 부른다.

  - 지어낸 고유어로 바꾸지 않는다. 길, 물음, 판, 꼴, 훑기, 낱말, 잽니다, 칸 같은 말이다.
  - 쉬운 말은 처음 나올 때 풀어 설명하는 것이지 이름을 바꾸는 것이 아니다.
  - 저장소의 옛 글에 이런 말이 남아 있어도 따라 쓰지 않는다. 옛 글을 일괄로 고치지도 않는다.

## 12. 하지 말 것

- **비밀 값:** 파일·기록·커밋·PR·로그·보고에 넣지 않는다. 키·토큰·비밀번호·계정 ID·실제 이메일도 마찬가지다.
  - 시험의 가짜 이메일은 `example.com`·`example.org` 같은 `example` 도메인만 쓴다.
  - 동희님께 키를 채팅에 붙여 달라고 하지 않는다.
- **유료 AI 호출:** 0번이다. `npm run eval -w server -- --real`은 돌리지 않는다(B 몫).
- **진짜 외부 서비스:** Supabase·카카오·Cloudflare 계정을 쓰거나 부르지 않는다. 바깥 공식 문서를 읽는 것은 된다. 읽으면 확인 날짜를 적는다.
- **배포:** 하지 않는다. 배포 설정을 쓰는 것은 되지만, 실행은 B가 한다.
- **B 몫 파일:** 3절의 B 몫 파일을 만들거나 고치지 않는다.
- **결정 무시:** 동희님 결정·품질 HOLD·설계 결정을 임의로 바꾸지 않는다.
- **생성 파일:** 손으로 고치지 않는다.
- **오래된 파일:** 오래됐다는 이유만으로 지우지 않는다.
- **자동화:** cron·daemon·전역 hook·숨은 자동 저장을 더하지 않는다. 앱 기능으로 설계된 Cron(일 실행기)은 된다.
- **확인하지 않은 것:** '확인함'이라고 쓰지 않는다. 틀린 통과(실제로는 안 되는데 통과로 보임)는 틀린 실패보다 나쁘다. 기계로 확실히 가를 수 없는 것은 통과로 두지 않고 사람 확인이나 닫힘으로 둔다.

## 14. 알려진 함정(앞 개발에서 배운 것)

1. **커밋 없이 길게 가지 않는다.** 한도에 걸리면 작업 트리만 남는다.
2. **원본 ID를 기억으로 쓰지 않는다.**
   - 예: 운영자 API는 API-004 로그인, API-005 `GET /operator/me`, API-006 로그아웃이다. 기억과 달랐던 적이 있다.
   - 06 `x-corthex.id`로 확인한다.
3. **공통 규칙은 G1~G10이다.** 정규식 `G\d`가 G10을 G1로 읽은 버그가 있었다(지금은 `G\d+`).
4. **플러그인 경로.** 검사 도구가 플러그인 폴더 이름(`corthex` → `corthex~g2`)에 묶여 깨진 적이 있다. 이제 `tools/corthex/` 사본을 먼저 쓴다. 사본은 손으로 고치지 않는다(`tools/corthex/README.md`).
5. **시험이 헛돌지 않게 한다.** 일부러 넣은 표시를 검사가 찾는지 먼저 본다(TASK-025 평문 스캔). 조건을 하나씩 빼 시험이 실패하는지 본다(TASK-021).
6. **같은 응답 시험.** 존재를 알리지 않아야 하는 경로는 상태·헤더 이름·본문(`traceId`·`instance` 제외)이 같은지 시험한다. 시간 차이도 줄일 수 있으면 줄인다.
7. **PostgreSQL 로그.** PostgreSQL은 제약 위반 행 값을 로그에 남긴다. 평문 개인정보를 제약 컬럼에 보내지 않는다(TASK-025 37).
8. **동희님 말 '추천 모두 승인'(2026-11-16 17:01 무렵).** TASK-003(Supabase Auth + TOTP)과 사진 EXIF '저장 전 모두 지움'의 근거다. 기록에는 뜻으로 적고 원문은 progress.md에만 둔다.
9. **역할 나눔(동희님 2026-11-16 17:11 무렵 "야 넌 개발만 끝내 직접 해보는건 다른 클로드 계저에서 할게").** 개발 세션은 진짜 환경 확인을 하지 않는다. 그 확인이 끝난 조건에 있으면 끝남 표시를 하지 않는다.
10. **CI 실행 번호는 GitHub에서 읽은 값만 적는다.** 다른 세션이 알려 준 값이면 그렇다고 적는다.
11. **목업 검사 높이 차이.** 09 토큰의 글꼴은 IBM Plex Sans KR이다. 환경에 없으면 대체 글꼴로 줄바꿈이 달라져 mockup 검사 높이가 어긋난다(PR #74 때 13/14, Claude 환경 PR #73·#75 때 14/14). page-check 결과의 '실린 글꼴'을 보고, 없으면 그 글꼴(OFL)을 로컬에 설치하고 다시 돌린다. 09 기록값과 검사 기준은 고치지 않는다.
12. **겹친 방어 시험.** 앞 단계 비교와 뒤 단계 실패가 같은 응답을 만들면, 앞 단계를 빼도 시험이 가르지 못한다. 앞 단계만 보이는 관찰(예: 바깥 서비스를 부르지 않음)을 시험에 더한다(fix-log (417)).

13. **Workers의 HTTP 리디렉션 정책.** 서버 `fetch`의 `redirect: "error"`는 Workers에서 TypeError를 낸다. 직접 `fetch` 옵션을 지정하는 서버 어댑터는 지원되는 `manual`을 쓰고300대 응답을 성공으로 처리하지 않는다. Node 도구의 `error`와 구분하며 Node 모의 시험만으로 Workers 지원 여부를 판단하지 않는다([실제 런타임 비교](../records/kakao-worker-fetch/2026-11-24/checks.md)).
